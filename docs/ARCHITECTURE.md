# 架构说明

本文解释 AI Company Framework 的总体架构与核心机制，供贡献者、插件作者和想深入了解的用户阅读。

> `v0.1` 是运行在 DeepSeek Harness / DSH Desktop 之上的 Skills Starter Kit。团队、会话和工具由 Harness 执行；本项目用 Skills、模板和 SOP 约定编排方式。声明式配置编译器、代码化模型路由和插件加载器属于 `v0.2` 计划。

### 1.1 分层关系

| 层 | 负责内容 |
|----|----------|
| [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) | 模型、工具、持久会话、Skills、插件运行时 |
| [DSH Desktop](https://github.com/dataelement/dsh-desktop) | 桌面交互、AgentTeams 活动面板、员工侧边栏、模型改配 |
| AI Company Framework | 岗位模板、模型分配策略、任务图规则、质检交付、飞书方案、实例隔离 |

AI Company Framework 只依赖公开的 Harness 能力，不复制或替代底层运行时。

## 2. 核心概念

### 2.1 会话即公司（硬隔离）

- 一个顶层会话只绑定一家公司；
- 公司根目录 = `<workspace>/companies/<DSH_SESSION_ID>/`；
- 团队名 = `company-<行业缩写>-<sessionShort>`（会话 ID 前 12 位起）；
- 一切业务内容只写公司目录内，禁止读兄弟公司。

> 隔离是**安全特性**：不会出现 A 公司的数据出现在 B 公司的交付里。

### 2.2 老板（总控 Agent）

用户只与老板对话。老板职责：

1. 需求解析（一句话 → 岗位清单，最多问 1–2 个问题）；
2. 模型路由（先实时盘点 `list_available_models` 再分配）；
3. 建司（创建团队、员工、公司目录、入职）；
4. 调度（按依赖图派任务）；
5. 质量闭环（抽查验收、打回返工、三次护栏）；
6. 交付（打包 + 假设清单）；
7. 经验沉淀（去敏写入 company-wisdom）。

### 2.3 员工（AgentTeams 成员）

- 每个员工是持久化子 Agent：有独立会话、邮箱和 Skill 文件；
- 入职时按 `company-role-template` 补全自己的技能；
- 用户可在员工侧边栏查看独立对话、直接发消息并单独修改模型；
- AgentTeams 活动面板显示成员状态、任务归属、依赖图和进度；
- Skill 可以持续维护，但接口契约变更须老板确认；
- 员工会话连败超过护栏次数时，由老板 reassign 或接管。

### 2.4 模型路由

建团队前先读取当前可用模型列表。路由策略按岗位需要选择：

| 岗位特征 | 路由原则 |
|----------|----------|
| 看图、视觉质检 | 使用支持图像输入的模型 |
| 策划、研发、复核 | 使用强推理模型 |
| 文案、客服、批处理 | 使用速度较快、成本较低的模型 |
| 长时间运行任务 | 考虑价格、Token、账号配额和稳定性 |

`v0.1` 的路由决策由 Skill 规则驱动，并通过 Harness 的模型列表和员工侧边栏执行；`v0.2` 计划提供代码化路由器和预算记录。

### 2.5 流水线（P0–P7）

| 阶段 | 内容 |
|------|------|
| P0 | 需求解析：一句话 → 行业/岗位 |
| P1 | 模型路由：盘点 → 分配 |
| P2 | 一键建司：团队/目录/入职 |
| P3 | 飞书接入（可选，与 P4 并行） |
| P4 | 任务调度：依赖图 + 并行 |
| P5 | 质检闭环：验收/打回/返工 |
| P6 | 交付打包：清单 + 假设 + 验收点 |
| P7 | 经验沉淀：去敏入库 |

### 2.6 经验库

- 位置：`<harness>/company-wisdom/`（common.md + 各岗位.md）；
- 只存**去敏的工作流程经验**（工具坑、最佳实践）；
- 严禁业务敏感数据；允许修订/推翻（旧条目标注取代）。

### 2.7 公司与工作流

“公司”是对非开发者友好的组织方式，不是执行层限制。岗位可以替换为任意工作流节点，只要定义：

1. 节点职责；
2. 输入和输出文件；
3. 上下游依赖；
4. 验收标准；
5. 使用的模型和工具。

因此，同一套机制也能组织研究报告、内容生产、软件开发、数据分析、视频制作和客服流程。一个顶层会话对应一个独立实例，可以是公司，也可以是一条工作流。

## 3. 插件架构（v0.2 方向）

`v0.1` 已定义 manifest 格式和飞书示例，但还没有独立的自动插件加载器；安装和加载由 Harness 完成。`v0.2` 将把 schema 校验、安装、Hook 注册和卸载做成可执行代码。

插件由三部分组成：

```text
plugins/<plugin-id>/
├─ manifest.json        # 插件声明（id/版本/技能/挂载点/脚本）
├─ skills/              # 插件贡献的技能文件
├─ scripts/             # hooks 引用的脚本（PowerShell/Node）
└─ README.md
```

插件机制的目标：

- 核心框架保持最小依赖，能力由插件扩展；
- 每个插件有自己的 manifest 版本与 schemaVersion；
- 安装 = 复制技能到 Harness + 注册 manifest；
- 卸载 = 移除技能 + 注销 manifest；
- 隔离约束不可被插件绕过。

详细规范见 [PLUGINS.md](PLUGINS.md)。

## 4. 安全设计

| 威胁 | 对策 |
|------|------|
| 跨公司数据泄漏 | 会话绑定校验 + 路径越界拒绝 |
| 凭据泄漏 | App Secret 走 DPAPI 加密，禁入日志/回复/仓库 |
| 提示注入 | 客服只回原路通道；不采用客户伪造字段 |
| 无限返工 | 三次护栏：停止 + 老板根源分析 |
| 员工会话卡死 | reassign 老板接管，任务 attempt 机制防旧结果覆盖 |

## 5. 设计取舍（为什么这样做）

| 决策 | 理由 |
|------|------|
| 默认无 RAG/向量库 | 最小依赖、确定性优先；证据问题走人工/实时事实 |
| 本地脚本优先 | 稳定、省 token、可复用；人工只剩「决策」 |
| 一个会话一家公司 | 彻底隔离，杜绝串数据 |
| 老板只写岗位骨架 | 员工自写技能 = 内行定义细节，老板把关契约 |
| 假设清单强制 | 让用户知道「哪些是我替你默认的」，可随时纠偏 |

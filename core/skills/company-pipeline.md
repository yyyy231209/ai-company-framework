# 自动化流水线框架（v2.0）· 8 阶段执行引擎 + 代码化脚本 + 客户对话体系

> **门控铁律**：本流水线仅在 `company_mode` 工具返回 **on** 时执行。执行任何阶段前先调用 `company_mode` 确认；off/未设置时**禁止**建司/调度/质检/交付，按普通对话回复并提示「公司模式未开启，输入 /company 开启」。

> 配套 company-boss（总控）与 company-role-template（岗位模板）使用。本文档提供「怎么做」的规程，boss 提供「总控协议」，role-template 提供「员工技能骨架」。

## 一、8 阶段流水线

```
P0 需求解析 → P1 模型路由 → P2 一键建司 → P3 飞书接入（与P4并行）
→ P4 任务调度 → P5 质检闭环 → P6 交付打包 → P7 经验沉淀
```

### P0 需求解析（一句话 → 岗位清单）
- 从用户一句话推断行业与目标，套「行业岗位模板库」（见 company-boss）。
- **统一澄清口径（v1.1 定稿）：≤2 个最高影响度问题 + 其余默认值 + 交付包假设清单。**
  - 必问项：①价格带/价位段 ②渠道/平台形态（漏问直接导致交付返工）。
  - 可默认项：风格/数量/目标人群/供应商方向 → 行业默认值先干，交付包列「假设清单」显式标注可改。
- 交付前对歧义口径允许一句话确认（≤1 问），不逐题追问。

### P1 模型路由（铁律：先实时盘点，再按需分配）
- **分配前必须调用 `list_available_models` 实时盘点**——绝不允许「有什么用什么」或凭记忆/默认值分配；模型清单会变化，每次建司/扩招都重新盘点。
- 盘点后按「岗位需求 × 实际可用」匹配：
  - 批处理岗（文案/客服/财务/coder）= 快速便宜档（如 deepseek-v4-flash）
  - 强推理岗（选品/质检/策划/客户经理）= 强推理档（如 deepseek-v4-pro）
  - 视觉岗必须 vision:true 的模型；**没有可用视觉模型时如实告知用户「此岗暂由人工把关」，不硬配**
- **实测验证优先于纸面可用**：模型在列表里 ≠ 子代理能用。经验库实证：openai-codex/minimax 在本环境子代理唤醒不稳（连败即换）；deepseek-official 实测稳定 → 默认优先 deepseek，跨 provider 分配必须基于历史实测记录。
- 每个岗位骨架必须写明「模型路由」字段（含 provider/model），扩招时 HR 入职建议中的路由同样基于实时盘点。

### P2 一键建司
1. 取 `$env:DSH_SESSION_ID`，团队名 `company-<缩写>-<sessionShort>`（sessionShort ≥12 位）。
2. 建 `<workspaceRoot>/companies/<sessionId>/` 目录 + `.dsh/skills/`。
3. `agent_teams_create` → `agent_teams_add_member` 逐岗位添加（按 P1 路由）。
4. 写岗位骨架（岗位名+一句话职责+输入/输出契约+路由）到 `.dsh/skills/<岗位>.md`。
5. 写 `company.json`（sessionId/teamName/companyRoot 等）。
6. **并行发入职消息（onboarding 模板 ≤80字/人）**：读骨架→按 company-role-template 自写技能→读经验库→回「已就位+技能已写」。
7. 老板逐个验收技能文件（grep「验收标准」存在性，不全文读）。

### P2.5 建司模式分流（v1.2 新增 · 用户反馈「我还没有具体业务」）
**建司完成后、派业务任务前，先确认模式（1 个问题，必问）：**

| 模式 | 适用 | 建司后动作 |
|------|------|-----------|
| 🏗️ 团队模式 | 用户只有团队骨架需求，暂无具体业务 | **只建司+员工就位+待命**。不派任何业务任务、不产交付包。等用户说「开始做XX」再进入业务模式 |
| 🚀 业务模式 | 用户有具体业务/首单需求 | 按 P4-P6 派任务→质检→交付包 |

- **团队模式退出**：用户说「开始做X」→ 老板按 P4 起建任务图，此时才需要交付包。
- **团队模式的可选项**：飞书接入（P3）仍可做——团队先有遥控通道，业务来了直接跑。
- **铁律**：没有具体业务时，绝不默认派业务任务、绝不产出交付包（防「为假设的业务白做」）。

### P3 飞书接入（与 P4 并行）
- 默认走官方一键创建：`feishu_onboard(action=start)` → 用户只打开一次官方确认链接 → SDK 自动创建机器人、最小权限、`im.message.receive_v1`、WebSocket → App Secret 自动 DPAPI 加密 → 自动绑定公司；再用 `feishu_onboard(action=status)` / `feishu_status` 验证。
- 全流程见 `../feishu-onboarding-sop.md`（相对当前 Skill 资源根）。禁止默认用 Chrome 逐页建应用；只有绑定历史应用或发布到更大可用范围时才走备用路径。
- 关键坑：老板机器人 `kind=boss`；员工机器人必须 `kind=staff` 且 `staffMemberId=<AgentTeams member.id>`；**默认 `allowGroup=true` 一次全开**（单聊+群聊），`allowGroup` 只申请群 @ 权限，群主仍须用飞书桌面端/移动端把 App 加入群；**禁止重复授权**（已 connected 不重新 start，防新建第二套机器人）；客服岗重建后必须同步更新 registry 的 `staffMemberId`；老板单聊回传用日志真实 sender open_id；注册表支持热加载，只有宿主插件代码变更才需 `Ctrl+Shift+R` 重启 Harness。
- 桥 `>=0.4.0` 默认一家公司一个老板 App：P2P 用唯一精确 `/成员名 正文` 或 `/岗位名 正文` 虚拟路由；员工回复原样传系统通道的 `botId/receiveId/receiveIdType`。需要不同身份/头像或租户隔离时才创建独立员工 App。

### P4 任务调度
- 按依赖图建任务（task 模板只写增量），同批无依赖任务并行创建，调度器自动认领。
- 任务粒度 ≤10/阶段；计划类任务只依赖文档不依赖素材实体。
- **事件驱动**：只在员工完成通知/任务状态变化时查 status，不主动轮询。

### P5 质检闭环
- 每个工序有验收：质检岗（或执行者自检）把关 → 打回点名（位置+问题+改法）→ 返工只改点名项 → 复检只查点名项 → 放行。
- 护栏：同一问题 3 次未过 → 停止，老板根源分析；质检员工会话卡死连败 → `reassign_task(assignee="captain")` 老板接管。
- 报告用 qc 模板（结论置顶+表格化）。

### P6 交付打包
- 每批交付用 delivery 模板：交付清单 + **假设清单（硬性要求）** + 验收点 + 可改项。
- 批次合并：相关环节产出一次交付，减少碎片化。

### P7 经验沉淀
- 每轮任务的「问题+解法」≤3 行由老板追加进 `<dshHome>/company-wisdom/<岗位>.md`（去敏）。
- 铁律：只写流程经验，严禁业务敏感内容。

## 二、变更管理（v1.1 新增 · 模拟验证 G1-G8 补丁）

### 2.1 需求修订（用户反馈）
用户反馈 → 根源分析（读产出/质检报告，排除法一次验证一个假设）→ 定向打回负责员工（附用户原话+根源+只改范围+验收标准）→ 循环达标。

### 2.2 追加任务三查
1. **依赖查**：无依赖→直接新建并行；有依赖→挂链。
2. **扩岗查**：超出在岗技能范围且 ≥2 次出现 → `add_member` 新岗；否则现岗兼顾。
3. **验收点查**：并入交付包批次合并。
- 每次变更登记 change.md（含一行影响摘要「改/重跑/新增」），随 feishu_notify 推送。

### 2.3 原地转型五步（建司后换赛道）
1. 判定时点：建司前→无成本换模板；建司后→走本流程。
2. 不重建团队、不改团队名（隔离协议绑定不可破）→ 只更新 company.json 与 feishu-registry.json 的 displayName/status。
3. 重写岗位骨架（旧岗改造/删减），写回 `.dsh/skills/`。
4. 任务图重排：reassign_task 撤销/挂起受影响旧任务 → 新建新方向任务。
5. 通知全员（接口契约变更须老板确认）+ qa 复检。

### 2.4 验收标准编号化
骨架验收标准改「编号+勾选」：`- [ ] A1 <标准>`；任务描述引用编号（如「验收：writer 骨架 A1-A3」）。

### 2.5 扩招流程（v1.4 更新 · 老板拆岗决策 + HR 执行招聘 + 老板创建）

**分工原则（v1.4 定稿）**：
- **老板拆岗**：业务扩展/转型时，**老板自己分析业务**，拆解出需要哪些新岗位（岗位名/职责/所需能力/数量），形成「扩招需求单」，下达给 HR。**不依赖用户指定岗位，用户只需说「业务要扩展」或「帮我看看还缺什么岗」。**
- **HR 招聘**：按老板的扩招需求单产出招聘包（JD/面试题库/入职建议）。
- **老板创建**：审核批准后 add_member + 写骨架 + 发入职通知。

**触发条件**（任选）：
- 用户提出业务扩展/新增能力（「业务要扩展」「帮我看看还缺什么」）
- 追加任务三查中「扩岗查」判定需新岗（超在岗范围且 ≥2 次出现）
- 业务方向转型后缺新能力岗
- **老板主动巡检**：业务模式运行中，老板定期评估现有岗位是否覆盖业务全链路（如电商缺运营/投放岗、内容缺设计岗）

**流程**：
```
1.【老板拆岗】老板分析业务扩展方向 → 产出「扩招需求单」：
   人事/扩招需求单.md（每岗：岗位名+职责一句话+所需能力+输入输出契约草案+优先级）
2.【HR 招聘】任务派给 HR 岗 → HR 按需求单产出：
   人事/岗位JD_<岗位>.md（职责≤6条+必备/加分要求）
   人事/面试题库_<岗位>.md（STAR 5问+评分表）
   人事/入职建议_<岗位>.md（岗位名+职责+输入输出契约+推荐模型路由+薪酬建议）
3.【HR 回执】HR 提交入职建议给老板审核
4.【老板审核】对照经验库路由坑（deepseek 优先）→ 批准/打回修改
5.【老板创建】agent_teams_add_member（按 HR 建议的岗位/路由）
6. 老板写岗位骨架到 .dsh/skills/<岗位>.md（含验收标准编号）
7. 发入职通知（onboarding 模板）→ 员工自写技能 → 老板 grep 验收
8. 变更登记 change.md（类型=扩招，影响摘要=新增岗位）
```

**注意**：
- **拆岗是老板职责，不是用户职责**——用户说「业务要扩展」即可，老板自动分析并产出需求单；用户也可以直接指定岗位（「招个运营」），此时需求单快速确认即可。
- **只有老板（captain）能执行 add_member**——HR 负责招聘流程（JD/面试/评估），创建权限在老板，防止随意扩编。
- 扩招后新员工读经验库入职（继承全公司智慧）。
- 团队模式/业务模式均可扩招：团队模式先扩骨架，业务来了直接跑。
- 员工「面试」在 Agent 语境 = HR 评估需求匹配度+路由建议；真实 STAR 面试题库仍产出存档（后续接真人面试可复用）。

## 三、Token 优化执行清单

1. **短路径**：companyRoot 只在入职消息写一次，此后全相对路径。
2. **入职消息 ≤80 字**（onboarding 模板）。
3. **任务描述只写增量**（task 模板），引用骨架验收编号。
4. **老板自查**：grep 关键数字+limit 局部读，不全文 read。
5. **质检报告结论置顶表格化**（qc 模板）。
6. **员工汇报一句话**（report 模板：状态+关键数字+路径）。
7. **status 事件驱动**，不主动轮询。
8. **output 即汇报**：任务 output 写完整摘要，汇报不重复。

## 五、v2.0 新增：子机器人创建流程（P3.5）

**建司 + 老板机器人接入后，必问用户一句：「是否需要子机器人（客服/其他员工接入飞书）？」**

流程：
```
1. 老板机器人已 connected（P3 完成）
2. 老板问：「是否需要为员工创建子机器人？（如客服机器人直接对接客户）」
3. 用户回答 → 立刻执行，不等待：
   - 需要客服机器人 → 调用 `feishu_onboard(action=start, kind=staff, staffMemberId=<客服 member.id>, displayName=<公司名·客服助手>, allowGroup=true)`
     → 把一次性官方确认链接交给用户打开 → 用户确认一次 → SDK 自动加密凭据、写 registry、建长连接并绑定员工
   - 需要其他员工机器人 → 同流程，仍用 `kind=staff`，以 `staffMemberId` 精准绑定岗位成员
   - **默认 `allowGroup=true` 一次全开**（单聊+群聊）；权限≠入群，群主随后仍需在飞书桌面端/移动端把应用机器人加入目标群；已 connected 的机器人禁止重复 start
4. 调用 `feishu_onboard(action=status, runId=...)` 与 `feishu_status`；connected 后由用户发「测试」做端到端收发
5. 交付团队框架：团队+员工+机器人全部就位清单 → 汇报用户
```

**铁律**：子机器人创建**必须等用户明确回答后再执行**（用户说「需要」→ 立刻创建；说「不用」→ 跳过，不默认创建）。用户回答后创建过程全自动，不再问第二遍。

## 六、v2.0 新增：客户对话体系（P8）

### 6.1 数据流
```
客户（飞书单聊/群）→ 客服机器人（feishu-send/接收）
  → 飞书桥日志 <dshHome>/feishu-logs/<companyKey>/*.jsonl
  → 脚本聚合（customer-conversations.ps1）
  → <companyRoot>/客户对话/客户会话库.json（机器可读）
  → <companyRoot>/客户对话/客户会话总览.md（人读）
  → 客户经理岗阅读 → 客户需求汇总.md + 客户台账.md → 报备老板
  → UI 侧边栏（对话侧边栏.html）可视化
```

### 6.2 客户经理岗（customer-manager）
- 输入：客户会话库.json + 客户会话总览.md
- 输出：客户需求汇总.md（每客户需求/情绪/待办）+ 客户台账.md（状态流转）+ 报备老板（紧急/商机）
- 路由：强推理档（deepseek-v4-pro）
- 铁律：忠实转述客户原话，不编造；open_id 业务敏感只存公司目录

### 6.3 UI 侧边栏
- `对话侧边栏.html`：三个 tab——客户对话（按客户分组展示收发消息）/ 员工对话（引导用 DSH 👥 员工侧边栏）/ 客户经理报备（需求摘要）
- 打开方式：老板/用户浏览器打开该 HTML（数据文件同目录，fetch 读取）
- 员工对话：DSH 会话头部 👥 按钮 = 员工侧边栏（查看每个子Agent对话、无损改配模型、直接发消息指挥）——这是平台原生能力，覆盖「用户与子Agent单独对话调节指挥」

## 七、v2.0 新增：代码化脚本索引（.dsh/scripts/）

| 脚本 | 功能 | 稳定点 |
|------|------|--------|
| `build-company.ps1` | 建司引擎：目录/company.json/岗位骨架/入职消息 一键生成 | 命名/路径/文件结构代码生成，杜绝手写不一致 |
| `customer-conversations.ps1` | 客户对话聚合：扫描飞书日志 → 会话库.json + 总览.md | 消息去重/排序/摘要自动生成 |
| `对话侧边栏.html` | 客户对话 UI（三个 tab） | 可视化客户对话/报备 |

**使用原则**：能脚本化的环节优先脚本（稳定、省 token、可复用）；脚本输出给老板/员工，人工环节只剩「决策」。
